## 日常协作

1. **同一时间只有一个助手修改这份工作区；另一位只检查。** 用户交接后再换人，不同时改代码、切分支或合并。
2. 干净的 main 用 `git pull --ff-only` 更新；有改动或合并未完成时先保留并交接，不执行强制同步。
3. 从最新 main 开带票号的分支。Codex 用 `codex/KAN-编号-说明`，Claude 可用 `KAN-编号-说明`。

## 执行单边界与需求变更（规则来源）

适用于 Jira KAN 的故事/任务、对应 PR、`.claude/commands/jira/*` 与 `.claude/templates/*`。会议、调研、Epic 与上线验收各有自己的完成条件，见本节末。2026-09-22 起生效；此前建的票按本节整理时，只重排结构、不无声删减已批准范围。

### 一张票 = 一个可独立审阅、验收的交付结果

- 拆分只看**能否独立验收**：拆出来的每一批都要有自己的用户可见结果和最小验收。不按文件数、字数、前后端、或「一轮聊天能否做完」拆票；必须同时生效的修复、权限控制和数据一致性保障不拆开。
- 拆分不是取消需求，也不自动改变承诺日期；要改日期、优先级、父子关系时单独提出。
- 不因为要减小票的体积而删掉安全边界、历史保全或必要的回归测试。

### 票面结构：当前有效正文 + 变更记录

正文只保留**当前有效**的执行要求，六块（操作形态见 `.claude/templates/ticket-story.md`、缺陷用 `ticket-bug.md`）：

1. **要得到的一个结果**——用户或下一张票能拿到什么。
2. **已确认的规则**——引用出处（会议日期、Jira 评论、用户指令）。
3. **本次做什么、明确不做什么**。
4. **已满足的前置与待决策项**——待决项写确认人；候选口径可以列，但**验收只按已决口径写**，未决的不预写成验收。
5. **本票关闭所需的验收**——可复跑的操作/接口/测试与期望结果，含拒绝、重复、回归。
6. **后续集成验证的归属**——真实账号、真机、云环境等本票做不到的验证，写明归哪张票或哪个里程碑；不笼统塞给 KAN-21/33。

末尾一节**变更记录**：一行一条「日期 · 改了什么 · 依据（谁在哪里决定的）」。被替换的旧要求整段移到 Jira 评论或变更记录，**不用删除线留在主清单里**，也不靠「以某条评论为准」修补错误正文。复现步骤、日志、历史讨论可以详细，但放在执行要求之后或评论里。

### 三个检查点

**开工前（`/jira start`、`/jira next`）**
读票面、评论、关联票与最近一次用户决定，写出本次的**范围基线**：交付结果、包含/不包含、已确认规则、待决项、本票验收。多版正文或评论互相冲突时，以**最新的明确用户决定**为准，找不到就问，不从多版正文里猜。基线回帖到票一次；只在实质变化时再帖，不每次读票都追加。

**实施中**
发现票面之外的东西，先分四类再动手：

| 类别 | 处理 |
|---|---|
| 本次改动引入的回归 | 本票必修，不另开票 |
| 实现原目标不可缺少的修复 | 本票做，记入变更记录并说明为什么不可缺 |
| 独立的既有缺陷 | 先查重、复现；已有票就补证据，没有就按 `/jira bug` 建缺陷票并 relates，**不扩当前 PR** |
| 新需求或独立目标 | 只提草稿（`/jira finding`），不进本票 |

凡影响**范围、业务行为、数据迁移、权限、验收、成本或排期**的，先写清变化与代价，问用户，在答复前停止依赖该决定的工作（其余独立工作继续）。得到决定后同步当前正文、验收、受影响的依赖说明与 PR。同一会话里的明确新指令即是授权，记下出处；找不到出处的不写成「已拍板」。已批准范围内的技术实现细节自行处理。

**提 PR 前（`/jira finish`）**
把实际 diff 与已批准范围核对，按**有意义的业务行为或交付项**（不是逐文件、逐函数）列「范围核对」表：改动 → 依据（票面哪一条 / 哪条评论 / 哪天的用户指令）。没有依据的标「待确认」并在 PR 里提问，不用「顺手修了」「按同一规则延伸」带过。

**自动回写与这三张表的关系**（`scripts/jira_merge_decision.py`，PR 合入后由 `jira-on-merge.yml` 执行）：只看「本票关闭验收」表——没有「未验证／❌」且「范围核对」表没有「待确认」才转已完成；否则停在审查中并写明原因。「后续集成验证」表是归属声明，不影响判定。旧模板的 PR（没有这些标题）退回扫全部表格行。

### 各类工作项的完成条件

| 类型 | 完成条件 |
|---|---|
| 开发执行单 | PR 合入 + 本票关闭验收逐条有证据；后续集成验证已写明归属 |
| 缺陷单 | 复现 → 修复 → 能失败再通过的回归；无法复现的调查单只能标「无法复现，已结束调查」 |
| 会议票 | 纪要与决定回写到相关票或文档 |
| 调研票 | 结论文档 + 明确关闭或转成执行单；描述为空、日期过期不是关闭理由 |
| Epic | 子项全部完成 + 整体验收记录；不直接当开发单 |
| 上线／集成验收 | 真实环境实测证据（真机、真实账号、云资源）；配置文件、合并、部署成功都不能替代 |

已合入的票只接**修复该 PR 自身验收**的后续；新成果开新票，不按「同一主题」往已合入的票里挂。

### 依赖怎么标

- `blocks` 只用于**技术依赖**：不先做前一张，后一张无法开发或验收。
- 上线门槛（必须早于某次上线）、排期先后、等待业务决定，用 `relates` 加一句文字说明；不批量改已有链接。
- 开发能开始、能集成验收、能上线三种依赖分别写，不混成一个 blocks。

### 审批原则

可能需要用户决策的地方，先说明问题、可选方案、推荐与代价，等答复；已明确决定且仍适用的事项引用执行，不重复问；技术事实先核实，不把该调查清楚的问题包装成产品选择题；没有回复不代表同意。
