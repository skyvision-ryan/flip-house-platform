## 1. 产品是什么

为翻房公司提供围绕每套房运转的协作与数据系统：明确谁该做什么、怎样做、交什么、在等谁、由谁确认；让执行记录关联项目、文件、预算和实际支出。

**已明确需求（09-17）**：近期目标是让 Jesse 和团队每天能围绕每套房实际协作——看清所有项目进展、更新各自负责的信息、及时发现需要处理的事情。**从一个新项目开始跑通完整使用过程，再按反馈迭代。**

长期发展为可复用的翻房 SaaS，并逐步扩展成了解公司流程、历史成本和决策依据的房产 AI 助手。**近期不把 AI 自动化当作团队开始使用的前提**：先让人手动填得进去、看得明白，AI 再逐步接管整理工作。

FDE 的工作方式：进入真实业务 → 写出可执行任务与说明 → 带团队使用 → 记录例外和反馈 → 调整项目任务 → 将共性经验更新到模板。合理的项目例外允许存在，不能为了通用模板抹掉事实。

## 2. 三个产品方向如何连接

| 方向 | 主要使用场景 | 本轮取舍 |
|---|---|---|

| 房产 AI 助手 | 查事实、解释进展、整理汇报、找说明、预填和辅助办理 | 先有可靠数据与状态；本周保留规则助手，真实 LLM 不作为 demo 验收门槛 |

保持 Cloudscape 组件体系。阶段使用卡片/列表。**进度条不再是禁止项**：09-17 会上 Jesse 明确认可阶段进度展示，并要求结合预计工期与已用时间（例：计划九个月、第八个月仍未开工要能一眼看出）。纪律是**时间和事实分两条、各自标注刻度，不用时间流逝冒充完成**；不扩成复杂甘特图或自动排程引擎。既有界面差异在相关 ticket 中逐步处理。

### 近期要跑通的使用路径（已明确需求，09-17）

Jesse 要求的信息组织顺序是：**全部项目概况 → 单套房情况 → 本人负责的具体事项**。执行人员只能看到自己那几项待办被明确反对——设计、Permit、采购同时处理多套房，必须知道公司有哪些房子、分别在什么阶段。

首次使用从一个新项目开始，端到端走一遍：

> 创建项目 → 团队看见这套房 → 对应职责的人看到自己该做什么 → 更新信息 → 负责人看到变化。

任务分派、说明、状态和个人待办全部保留，只是不再作为唯一入口。

## 3. 项目、模板与任务

- 一套房对应一个 Project。
- **新建项目要填的基础信息（已明确需求，09-17）**：ARV／装修后预计售价、预计项目周期、房屋基本情况、历史交易信息（上一次什么时候、多少钱卖的）、土地用途／Zoning。**先支持手动录入并随时修改**；自动获取属于后续增强，不假设已有可用接口。具体字段名和 Zoning 术语以 Jesse 提供的样例进一步核对。
- **线索房做独立功能（已决定，09-17 会后）**：不再纠结「线索要不要进平台」——**做一个单独的功能专门管理线索房**。既有六段模板和线索阶段都不删；线索房在系统里等价于「停在 ① 预买房、`open escrow` 尚未确认」的项目，独立入口只负责把它们单独列出来管理。
- 目标模板六段：预买房 → 买房与过户 → 装修 → 预上市 → 卖房上市 → 售出收尾。五段旧版的映射在迁移中保留；不是直接改数组序号。
- Task 模板预设默认角色、操作说明、交付要求和完成规则；Task 实例保存具体账号、项目补充说明、到期日、状态和实际结果。
- 新项目生成自己的副本，项目内改任务不改变其他项目；模板更新默认只作用于以后新建的项目。
- 仅需要独立分派、独立期限或独立验收的事项拆为子任务；其余操作步骤放在说明的检查清单中。本周不要求实现任意层级嵌套。
- 每个任务有一个主要负责人，可记录协作者和等待方；D/J 审批人另行保存，不能用“一名负责人”取代双人确认。
- 角色管权限，账号接任务。同角色的两个人不应自动成为同一任务的负责人。

任务说明至少回答：目的、准备材料、执行步骤、参考资料、交付物、怎样算完成、遇到例外如何反馈。通用说明与本项目补充分开，先用普通文本和简单清单即可。

## 4. 状态、证据与完成

目标状态：未开始、进行中、等待、待确认、完成、不适用。任务状态独立于业务阶段；阻塞由明确前置未满足派生，逾期由到期日与未结束状态计算。

等待至少记录对象/事项及原因，可加预计回复日期；改期保留原日期和原因；不适用保留理由与操作人。哪些关键节点允许豁免仍是业务问题，普通任务的“不适用”能力不能绕过关键节点。

| 任务性质 | 示例 | 完成规则 |
|---|---|---|
| 一次性交付 | 提交指定版本的申请回执 | 符合该任务要求的交付物到齐；需要审阅的进入待确认 |
| 持续工作 | 施工、采购、permit 跟进 | 照片和记录是更新；明确范围的工作包交付并确认后才结束 |
| 审批或里程碑 | 可以开工、Final、交割 | 满足适用的事实前提，再由指定人确认；保留 D+J 双确认及最后一次 Final 检查通过规则 |

**审批规则的两种事实要分清（09-17）**：

- **当前实现事实**：六个关键节点各需 D 和 J 确认一次，两个都确认才过门；`final` 额外要求最近一次标 final 的检查通过；「负责人」角色可代勾并留痕。这是代码现在的行为。
- **倾向性结论（09-17 会后，尚未最终拍板）**：倾向把 **D 当作观察者**——关键节点由 J 确认即可，D 不是必须，项目可以继续往下走。**这条仍需和 David 本人确定**，不是已生效规则。
- **待业务决定**：在 David 本人确认前，**不取消既有的 D/J 双确认控制，也不擅自增加新的阻塞**；不把所有流程顺序解释为强依赖。稳定 step key、证据与历史保留的要求继续有效。

不能用“上传了一张施工照片”完成整个施工，也不能用保险单完成贷款。任务拆分与完成规则必须能表达这一点。

任务、个人待办、项目总览、更新记录和助手引用同一套业务状态。已有步骤证据通过稳定 key 关联到任务，迁移时保留文件、时间、审批人和手工确认来源；无法确认的历史记为待核验，不伪造已完成结果。

仅实施已经明确的依赖，允许并行工作。许可范围、贷款方、付款和收尾规则的开放问题逐项保留，不将所有流程图顺序推断为强制依赖。

**可见范围分三层（已明确需求 + 实施建议，09-17）**。项目存在和阶段要共享，**不等于**财务、凭证、合作商资料一并开放：

| 修改、分派与审批 | 谁能改、谁能派、谁能确认 | 仍按角色与项目成员判定，**不因为可见就可写** |

**待业务决定**：具体人员权限矩阵仍需 Jesse 确认。**在确认前不要把全部数据权限一次放开**。

保留决策、统筹、执行、外部四级权限意图及现有金额边界。首轮用管理员建独立账号，AWS 正式环境采用 Cognito 认证；应用维护稳定 user_id、角色和项目授权。Demo 可复用本地认证适配，不能将它误称为 Cognito。邮箱邀请、公司 SSO、完整承包商门户排在后续。

正式模式由后端验证登录会话；不能相信客户端自报身份。授权同时考虑角色、项目范围和动作；列表、搜索、下载、任务详情、更新记录与助手都遵守相同边界。

账号/角色和真实人员的对应是待落实配置，不能把未确认代号擅自映射为真实姓名。任务记录实际 user_id，角色快照仅用于解释当时权限和分工。

**职责优先于个人（已明确需求，09-17）**：先由 Jesse 确认公司流程和人员职责，再让员工使用并反馈操作困难与实际例外。按职责组织工作、具体账号承接任务；**换人之后仍能理解并继续同样的工作**，不为每个人单独设计一套互不相通的系统。Jesse 本人和协助她统筹的人需要整体视野。

**代号沿用字母（已决定，09-17 会后）**：职责已经明确，**继续使用现有的字母代号**（D、J、K、Z、S、W、A、L、PM、设计师等），真实姓名由 Jesse 稍后提供。在拿到之前不做任何代号到真实姓名的映射；会议文字稿里的姓名有转写错误，**不据此确定任何人员代号**。

**待业务决定**：最终人员名单、姓名拼写、外部参与者是否登录系统，均以 Jesse 确认结果为准。

**登录方式（已明确需求）**：第一版接受账号密码登录 + 手机访问 + 人工更新。微信接入**不是启动条件**（会上明确担心微信里的客户付款账号等敏感信息）。这不改变 AWS 正式环境仍用 Cognito 的既定方案，也不降低正式环境的安全要求。

## 7. AI 从问答到办理

| 阶段 | 能力 | 依赖与验收 |
|---|---|---|
| 当前 | 规则洞察与页面链接 | 明确标注规则生成；身份切换/退出后清理或重取上下文 |

### 最终采用的三层 AI 基础

**已决定的方向（09-18）**：项目后续的 AI 能力按 **Agent Skills → MCP 工具层 → Jev 式决策层** 的顺序建设。三者分工而不是互相替代：Skills 保存公司怎样做事，MCP 提供受权限控制的真实工具与数据，Jev 式模型只处理固定答案空间里的模糊判断。

| 基础层 | 大白话作用 | 本项目的首个落点 | 开工前提／验收 |
|---|---|---|---|
| Agent Skills | 给 AI 可版本管理的岗位 SOP | 先保留已有 `jira-next` / `jira-finish` 开发流程，再从「新项目建立」「保险切换检查」「贷款资料检查」「团队试用验收」中逐个拆业务 Skill | 每个 Skill 只引用现行规则，明确触发条件、停止点、人工决定与测试样例；不把待定业务规则写成确定事实 |
| MCP 工具层 | 给 AI 带权限的标准插座 | 第一版只读：查可见项目、项目阶段、任务与待处理事项；Jira / AWS 只作开发运维连接，不与业务用户权限混用 | 依赖 KAN-21 的稳定 `user_id` 、项目成员与动作授权；列表、搜索和详情使用同一边界；每次调用可审计，越权反例必须测试 |
| Jev 式决策层 | 给系统一个会说「我不确定」的智能分诊员 | 现场更新归类、卡点／请示识别、助手工具路由；先跑 shadow mode，不改业务数据 | 依赖 KAN-21/28/29 的权限、状态、证据和审阅契约；用合成或去标识化样本评估每个用途，分别校准阈值，低信心回退到人或确定性规则 |

**组合路径**：用户输入一条现场更新 → 决策层只判断建议归属和风险信号 → Skill 提供公司对应流程 → MCP 只读取当前用户有权看的事实 → 界面显示建议与来源 → 用户确认后由后端重新验证权限和最新前提再写入。

**当前真实状态**：开发工作区已有三个项目级 Agent Skills：`jira-next`、`jira-finish` 和本次新增的 `flip-house-project-intake`；同时可见外部 MCP 连接配置。这些都是开发辅助，**不等于 Flip House 业务产品已接入 Skills / MCP**。除新项目启动检查外的业务 Skill、产品级 MCP server、Jev 或其他决策供应商均未实现。每一层开发时仍需对应执行单，不把本节当成已排期或已交付。

**近期定位（已明确需求，09-17）**：AI 自动化不是团队开始使用的前提。先让人手动填得进去、看得明白；AI 按上表逐级接管。会上讨论过的自动估值、区域打分、谈判辅助、自动下单、微信机器人**都不是近期承诺**。

### Jev / 类 System One 决策模型怎样用在本项目

**实施建议（09-18，非当前实现，也非近期验收门槛）**：Jev 不生成文字，而是用同一份状态回答事先定义好的 `Choice` / `Score` / `Noul`（选项／有序评分／是否概率），返回概率与信心信号。这类模型在本项目的正确位置是**“智能判断层”**，不是聊天界面、业务数据库或审批人的替代品。参考：[TypeSafe 介绍](https://docs.typesafe.ai/introduction)、[信心分流](https://docs.typesafe.ai/confidence)、[Vercel AI Gateway 集成说明](https://vercel.com/changelog/typesafe-ai-jev-now-available-on-ai-gateway)。

| 使用点 | Jev 只做什么 | 代码／人保留什么 |
|---|---|---|
| 现场更新归类 | `Choice`：把一句更新建议路由到任务、采购、水电气、贷款、保险或「其他」 | 高信心时只预填归属；中信心请用户确认；低信心不写入 |
| 卡点与请示识别 | 多个 `Noul`：这条记录是否表示「在等外部回复」「需负责人决定」「可能涉及安全」 | 只生成提醒候选；等待对象、截止日期、通知人与状态变更由用户确认 |
| 风险优先级 | 多个 `Score`：分开评估工期影响、成本影响、安全影响，再由代码组合 | 已过期天数、预算差额、到期日等可计算事实始终用确定性代码 |
| 助手问题路由 | `Choice`：选择「项目进度」「我的事项」「采购」「贷款」「保险」等有权限的后端工具 | 权限过滤在模型调用前完成；事实由工具返回；需要给人看的说明再交给生成式模型 |

**不交给 Jev 的事**：认证与授权、项目成员边界、金额计算、业务日期、任务完成与否、D/J 确认、Final 检查、自动下单、自动投保／取消、自动资金动作。固定选项能防止模型输出类型之外的答案，**不能防止它在合法选项中判错**；“信心高”也不等于已经验证正确。

**接入顺序**：等 KAN-21（身份／项目授权）与 KAN-28/29（状态、证据、审阅）的数据契约稳定后，再单独建可审阅的试点执行单。第一步只用合成或去标识化样本跑 **shadow mode**：保存问题／选项版本、模型版本、概率、延迟与人工真值，但不改业务状态。按真实标注数据分别校准每个用途的阈值，不设一个全局信心线。

**技术边界**：后端设一个供应商无关的决策适配层，前端不直连外部模型。发送前先用当前用户权限缩小状态，不传凭证原件、登录秘密、不必要的个人资料或完整财务信息。Jev 仍在 early access，接入前要实测本项目样本的准确度／校准度，并完成供应商、费用、故障回退、数据保留与处理条款审查；不因官方基准的速度／价格声称直接承诺生产效果。

**后续探索（会上明确可放第二阶段）**：设计文件与商品链接的自动整理；合作商资料库（承包商、园丁、Agent、Staging、材料供应商等）关联历史项目与报价；按房屋价位、风格和历史项目复用选材；微信、语音和更完整的 AI 助手；历史数据分析与辅助估算。历史数据可逐步补充，不作为启动条件。

AI 通过服务端业务工具获取有权限的数据；计算金额继续复用确定性代码。查询不到的信息应明确缺失，不能填造事实。解释超支/延期原因需要对应变更或现场记录，仅有总金额/日期时只能陈述偏差。

知识范围同时包含结构化项目数据和文本资料：任务说明、流程规范、相关文件、变更理由。先按项目/任务取相关资料片段；当资料规模和检索需求出现后再选择检索方案，不预设必须有向量数据库，也不永久排除文本检索。

模型只提出动作；服务端执行时验证当前用户、项目、允许字段与最新前提。审计中将操作者 user_id 与 assistant 来源分开，不篡改身份字符串代替真实用户。保持规则助手回退，记录问题、引用、调用与实际用量；模型/供应商、预算、数据处理边界在实际接入时核实，不沿用旧文档的粗估价格或 SDK 断言。
