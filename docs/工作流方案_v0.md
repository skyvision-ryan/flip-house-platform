# 翻房项目工作流：方案 v0（讨论稿，2026-09-11）

> 2026-09-15 状态说明：历史工作流讨论稿。文中“先不做登录”“移动端以后再做”及开发顺序已失效；依赖、等待、实例化等设计供参考。 当前 AI 入口见 [AGENTS](../AGENTS.md)，交付顺序见 [ROADMAP](../ROADMAP.md)，产品原则见 [当前方向](产品方向与执行原则.md)。本文件保留原始历史内容。

角色：产品架构 + 全栈 + 施工流程顾问。本稿只做分析与方案，不改代码。

## 1. 我对现有产品的理解

技术栈：React + Cloudscape（中文界面）/ FastAPI + SQLAlchemy 2 / SQLite，单容器部署在 Render，推 main 自动发布。没有用户与登录（顶栏是“演示账户”），没有迁移工具（启动时 create_all，库空则灌示例数据）。

现有实体：Property（房产 + 字段多来源）、Owner / Mortgage / SalesHistory、Project（策略、stage / substage、状态覆盖、买入 / 开工 / 完工 / 挂牌 / 成交五个日期、风险、备注）、BudgetLine / Expense、ProjectFile（类型、阶段、日期、对方、金额）、DealAnalysis。

已经存在、可直接复用于工作流的东西：

- Project 的五个日期就是五个里程碑的“实际日期”雏形，可作为里程碑任务的落点。
- `status.py` 规则状态（超预算 5% 为有风险、过完工日未挂牌为落后，人工可覆盖并留理由）。同一套“规则 + 可覆盖 + 说明理由”的模式直接扩展成任务级和项目级健康度。
- `insights.ts` 规则洞察（超支 / 落后 / 缺文件 / 缺数据）驱动工作台“需要关注”和助手抽屉，加“逾期 / 阻塞 / 等待外部”三类即可。
- LifecycleStrip 九段轨道 + 四个里程碑列，是阶段条的现成 UI，只需改成从工作流数据取值。
- WorkflowCards 三张卡（预算已用 / 距完工 / 文件登记），改成“正在做 / 在等谁 / 下一步”。
- ProjectFile 已有类型、阶段、日期、对方、金额，可作为任务完成证据的载体（许可证、检查报告、签署文件）。
- AssistantPanel 的规则问答，是进度汇报文本的天然出口。
- 工作台 Board 小组件机制，跨项目的“今日逾期 / 阻塞”组件可直接加进去。

技术债与缺口：无迁移工具（改表要手工）；无人员概念；stage / substage 是写死的字典，和真实六阶段流程不一致；日期是字符串；没有任何活动日志或审计。

## 2. 我对真实翻房流程的理解

原始文档 24 行，按“谁在等谁”重组后是 6 个阶段、5 道硬关口、若干并行工作流。阶段名是从原表推出来的，不是套模板。

```
阶段 1  房源与出价        J 筛选 → L 看房 → D+L 定价谈价        ═ 关口 Open Escrow
阶段 2  买入 Escrow       并行：J+K 贷款+保险 · D+L 签 loan doc · L 量尺 · 设计师设计 · K 开水电网
                                                              ═ 关口 Close Escrow
阶段 3  许可与开工准备    Z 申请 permit（每套房不同）           ═ 关口 开工
阶段 4  施工与验收        A 买材料（持续）· Z 按节点约 inspection（循环）· J agent 介入
                                                              ═ 关口 Final 检查通过
阶段 5  上市与销售        J staging · J 上市 · A 园丁剪草       ═ 关口 收 offer / Open 卖出 Escrow
阶段 6  卖出 Escrow 与收尾 并行：S+W 卖房文件 · K seller disclosure → D 签字 → K 关水电网、退保险
```

关键结构特征（这决定了数据模型）：

- 不是一条线，是多条并行工作流汇到关口。阶段 2 有五路并行，阶段 6 有两路并行后汇到 D 签字。
- 关口是“事件”不是“任务”：Open / Close Escrow、开工、Final 通过、收 offer，它们没有工期，只有达成日期。
- 施工内部在原表里是黑箱：只有“开始施工”“申请 inspection”“买材料”“final 通过”四行。真实施工是多个工作包，每个工作包后面跟一次检查，失败要整改再验。
- 多数任务不是“在做”，而是“在等别人”：等市政发许可、等检查员、等贷款方、等卖方、等设计师、等材料。

## 4. 成熟系统怎么做（含出处）

企业级施工系统（Procore、Autodesk Build、Buildertrend）和翻房从业者（BiggerPockets 等）的共性，逐项对我们的取舍：

| 概念 | 成熟做法与出处 | 我们 |
|---|---|---|
| 模板 vs 实例 | BPMN 的 Process Definition / Instance；Procore Action Plans 模板 → 计划（support.procore.com/products/online/user-guide/project-level/action-plans） | MVP |
| 阶段 + 任务 + 前置依赖 | Buildertrend 只支持 Finish-to-Start 与 Start-to-Start，带 lag / lead；前置移动，后置自动平移相同天数（helpcenter.buildertrend.net/en/articles/3480451） | MVP 只做 FS，可加 lag |
| 改日期必填原因 | Buildertrend 移动任务强制填 Shift Reason，并记录基线 vs 实际（buildertrend.com/help-article/schedule-overview/） | MVP |
| 球在谁手上 | Procore RFI 的 Ball In Court 字段，明确当前责任方（support.procore.com/products/online/user-guide/project-level/rfi） | MVP：任务的 waiting_on |
| 等待态显式建模 | Change Order 有 Pending-Pricing / Pending-Proceeding 等 11 个状态；Warranty Pending（support.procore.com/faq/what-are-the-default-statuses-for-change-orders-in-procore） | MVP：状态里单列“等待” |
| 检查失败 → 复验 | Procore Reinspect 生成子检查并链接父检查，已通过项保留（support.procore.com/products/online/user-guide/project-level/inspections/tutorials/create-reinspection） | V2；MVP 用“检查任务 + 结果 + 新一轮” |
| Punch List 完成 ≠ 关闭 | Procore：执行方 Resolve，Final Approver 才能 Close（support.procore.com/faq/what-is-the-punch-list-work-flow） | V2 |
| 变更事件 → 变更单 | Procore 两段式：先记潜在成本，报价后转正式变更进预算（support.procore.com/products/online/user-guide/project-level/change-events） | V2；MVP 只记一张“变更记录” |
| 日报 | Procore Daily Log 21 个分区，含 Delays 和 Change History（support.procore.com/.../daily-log-overview）；从业者要求承包商每天发照片 + 今日完成 + 明日计划 | MVP 用“任务更新流”代替日报，不单独做日报 |
| 短期滚动计划 / 约束日志 | Last Planner 的 3–6 周 Lookahead、Constraint Log、PPC（leanconstructionblog.com） | V2：等“承包商可靠度”有数据需求时 |
| 关键路径、浮动 | CPM 四种依赖、总浮动 / 自由浮动（onplana.com/blog/dependency-types-deep-dive） | 以后。小公司靠关口日期与 FS 链就够 |
| 每对象活动日志 | Procore Change History、Autodesk Issues Activity log | MVP 第一天就要 |

从业者视角（同样有出处）：

- 施工顺序与检查门槛（Phoenix / Portland / Madison / Santa Cruz 官方页面）：拆除 → 地基 / 结构（检查）→ 屋面外墙门窗 → 框架（检查）→ 粗装 HVAC / 水 / 电（各 trade 独立检查）→ 保温（检查）→ 干墙（部分辖区检查）→ 精装 → 各 trade final + Building final。“检查前不得覆盖”是硬规则；复检收费（Bellevue 每次 $145/小时）；无证开工会被停工。
- 常见延误（BiggerPockets）：承包商不按时进场或失联、许可拖延或停工、长交期材料（橱柜 6–12 周、台面放样排队、门窗 2–3 周）、拆除后发现隐患、检查失败复检、选材决策晚、上市后估价低。
- 汇报方式：行业没有标准周报；实际是承包商日照片 + draw 节点打包 + 预算 vs 实际；贷款方按 draw 要照片、发票、lien waiver（rcncapital.com）。
- 空白：没有任何翻房工具算“落后基线 N 天 × 日持有成本 = 损失 $X”。这是我们能做出差异的一点，而且数据很简单。

## 5. 我们现在的流程缺什么

对照上表，两份文档里缺的、需要在模型里留位置的：

- 施工黑箱：没有工作包，没有检查节点清单，没有失败 → 整改 → 复检的循环。
- 材料：只有“A 买材料”一行，没有长交期材料的下单 / 到货日期。这是从业者第三大延误源。
- 承包商：全文没有承包商对象，没有付款节点，没有变更单。
- 等待方：谁在等市政、贷款方、设计师、检查员，文档没表达，但这是经理每天追的东西。
- 卖出侧：收 offer 之后的买方检查期、估价、贷款审批、交割日期都没有，而“承包商留置权导致产权问题”对翻房尤其常见。
- 关口由谁宣布：没有“谁决定阶段结束”。
- 时间与成本影响：没有目标日期、没有基线、没有延误代价。
- 顺序疑点：园丁剪草在上市前后；水电网是 open escrow 后就开、还是 close 后；staging 是否必须等 final。

正确的地方：并行工作流的识别（阶段 2 和阶段 6）是对的；permit 因房而异、inspection 有时间这两句抓住了要害；负责人代号已经很清楚。

## 6. 推荐的 MVP 产品模型

一句话：把每套房变成一张“活的任务清单”，任务分阶段、有负责人、有前置、有等待方、有到期日，所有变化都留痕；系统只回答“现在卡在哪、卡在谁、下一步是谁的事、比计划晚了几天”。

核心规则（确定性的，不用 AI）：

- 任务状态只有 6 个：未开始、可开始、进行中、等待（外部）、完成、跳过。“阻塞”不是状态，是派生：任何前置未完成即为阻塞。
- 等待是主动标记：标“等待”必须填“在等谁”和“预计何时”。
- 关口 = 里程碑任务：工期为零，只有目标日和达成日；关口未达成时，下游任务全部显示为“等关口”。
- 改到期日必填原因，原值保留。
- 逾期 = 今天 > 到期日且未完成；项目落后天数 = 下一个关口的目标日 vs 基线目标日。
- 检查任务有结果：通过 / 未通过；未通过时新建“整改”任务和下一轮检查任务，链接上一轮。
- 有些任务要求证据：完成时必须挂文件或照片（许可证、检查通过、签署件）。

模板与实例分离：公司只有一份“翻房标准流程”模板（版本化）；新建项目时按模板生成任务副本，之后项目里随意增删改，不影响模板；模板改了只影响以后新建的项目。

## 7. 推荐的数据模型

新增 6 张表，不动现有表结构（Project 只加两三个字段）。

```
Person            人员字典：code(A/D/J…)、name、role、contact。先不做登录。
WorkflowTemplate  模板：name、version、is_active、created_at
TemplateTask      模板任务：template_id、key、phase、name、kind(task|milestone|inspection)、
                  default_owner_code、default_duration_days、depends_on_keys[]、
                  requires_evidence、is_optional、external_party、sort
Task              项目任务：project_id、template_key(可空)、phase、name、kind、
                  owner_person_id、status、waiting_on、waiting_until、
                  baseline_start/end、planned_start/end、actual_start/end、
                  result(pass|fail|null)、round(检查轮次)、parent_task_id、sort、note
TaskDependency    task_id、depends_on_task_id、type(FS)、lag_days
TaskEvent         活动日志：project_id、task_id、type(created|status|date_shift|assign|
                  comment|evidence|result)、old、new、reason、actor_code、file_id、created_at
Project 加字段    template_id、template_version、target_list_date、daily_holding_cost
```

对你列出的问题逐条回答：

- Phase 做实体还是枚举？枚举加模板里的顺序。阶段没有自己的属性，只是任务的分组和排序，做实体是过度设计。当前 substage 保留给线索阶段，施工后的 substage 改为从工作流派生。
- 里程碑要不要独立于任务？不独立。里程碑 = kind 为 milestone 的任务，工期为零。这样依赖、日志、UI 都复用，成本最低。
- 依赖怎么表示？单独的依赖表，一对多。一个任务可以依赖多个任务（D 签字依赖 S+W 文件和 K 披露）。
- MVP 要不要 SS / FF？不要。只做 Finish-to-Start 加可选 lag。原表五路并行是“同一关口后同时开始”，用共同前置表达即可，不需要 SS。
- 并行怎么做？没有特殊结构。两个任务前置相同、互不依赖，自然并行。UI 按阶段分组时并排显示。
- 外部等待怎么表示？状态 = 等待，加 waiting_on（文本或从人员字典 / 外部方字典选）和 waiting_until。这就是 Procore 的“球在谁手上”。
- 重复检查怎么做？检查任务失败时，系统建一个“整改”任务和一个 round+1 的检查任务，parent_task_id 指向上一轮；下游任务依赖“最新一轮通过”，实现方式是下游依赖指向最新轮次（自动改写依赖）。
- 完成证据？TemplateTask.requires_evidence；完成时校验该任务至少有一条 evidence 事件（挂 ProjectFile）。
- 工作流与静态模板的区别？模板是“通常会发生什么”，实例是“这套房实际发生了什么”。实例可增删任务、跳过、重复、改负责人、改日期，全部记 TaskEvent。
- 怎么实例化？新建项目时选模板（默认“翻房标准流程”），逐条复制 TemplateTask 为 Task，按 depends_on_keys 建依赖，按 default_duration 和关口目标日推算基线日期。
- 单项目改动怎么不影响模板？Task 是副本，只记 template_key 用于追溯。
- 模板版本？模板一旦被任何项目使用即冻结，修改生成新版本；项目记录 template_version。
- 历史怎么保留？只追加不覆盖：TaskEvent 记每次变更的 old / new / reason / actor；基线日期单独一列永不改。

正在做（3）           在等（2）                       逾期（1）

下面是按阶段分组的完整任务清单（阶段可折叠，当前阶段展开）；每行：任务名、负责人、状态徽章、在等谁、到期日、逾期天数、证据图标。点任务打开侧边抽屉：详情、依赖、更新流、挂文件。

工作台加两个小组件：“今日逾期与阻塞（跨项目）”、“在等外部方（跨项目，按对方分组）”。

## 9. MVP / V2 / 以后

MVP：人员字典；任务 + 阶段 + 负责人 + 6 态；FS 依赖 + 派生阻塞；等待方与预计时间；里程碑关口；到期日 + 基线 + 改期必填原因；活动日志；证据要求；模板实例化；工作流页签；日报 / 周报文本生成；工作台跨项目逾期 / 阻塞组件；落后天数 × 日持有成本。

V2：检查复验链（父子链接、已过项保留）；整改清单“完成 ≠ 关闭”；变更记录 → 进预算；长交期材料清单（下单 / 到货日）；卖出侧关键日期（检查期、估价、交割）；3 周滚动计划与“本周承诺完成率”；Lark 提醒。

以后：完整 CPM（浮动、关键路径自动计算）、SS / FF 依赖、承包商门户与移动端、只读合伙人视图、RFI 多角色流程、AI 从 WeChat 语音 / 照片抽取任务更新。

不做：Jira 层级（Epic / Feature / Sub-task）、Temporal / Camunda 一类流程引擎、事件溯源、微服务。SQLite + 六张表 + 几条规则足够支撑到几十套房并行。

## 10. 要问翻新负责人的问题（10 个）

1. 施工内部通常分哪几步？每步之后要不要市政检查？请用最近一套房从拆除到 final 顺一遍。
2. 检查没通过会怎样：谁约复检、一般隔几天、有没有因此停工？
3. 没拿到 permit 能不能先干活？哪些活不需要 permit？permit 是 close escrow 后才能申请，还是 escrow 期间就能提交？
4. 一个任务谁说“完成”？一个阶段谁说“结束”？关口（open / close escrow、开工、final、收 offer）由谁宣布？
5. 哪些事每套房都做，哪些视情况（设计师、园丁、贷款、loan doc）？全款买是不是跳过贷款和保险？
6. 你现在每天追着谁要什么信息？最常等的外部方是谁（市政、贷款方、承包商、设计师、供应商）？
7. 承包商谁管、有几家、按什么节点付款、临时加活怎么批？
8. 目标完工日和目标上市日怎么定的？每套房每天持有成本大概多少（贷款利息 + 水电 + 保险 + 税）？
9. 三个顺序疑点：园丁剪草在上市前还是后；水电网 open escrow 后就开还是 close 后；staging 是否必须等 final 通过。
10. 现在每天 / 每周向管理层报什么？管理层最在乎里程碑日期、延误、预算，还是任务完成数？

## 11. 开发切片

按“先让负责人能用、再让系统会算、最后让系统会说”的顺序。每片都能独立上线。

切片 1：任务清单能用（M）
- 目标：一套房的任务、负责人、状态、到期日能录能改，所有改动留痕。
- 数据：Person、Task、TaskEvent；Project 加 target_list_date、daily_holding_cost；引入 Alembic 做迁移。
- 后端：人员 CRUD；任务 CRUD（含状态流转校验、改期必填原因、等待必填对方）；事件写入；项目任务汇总接口。
- 前端：工作流页签（按阶段分组列表 + 任务抽屉 + 更新流）；先用手工建任务，从示例项目里把 24 行录进去。
- 验收：负责人能把一套真实房子的当前状态录进去，并从页面回答“谁在等谁、什么逾期”。
- 不做：依赖、模板、汇报。

切片 2：系统会算（M，依赖 1）
- 目标：阻塞派生、关口、逾期、落后天数与代价。
- 数据：TaskDependency；Task 加 kind、baseline 日期。
- 后端：依赖 CRUD；派生字段（blocked、blocked_by、overdue_days、next_gate、days_behind、delay_cost）；`status.py` 加“有逾期关口”规则。
- 前端：指挥中心头部三列 + 下一关口；阶段条改读里程碑任务；工作台两个小组件。
- 验收：改一个前置任务的状态，下游的阻塞 / 可开始立即变化；晚了几天和大约损失多少能显示。
- 不做：日期自动平移。

切片 3：模板与实例化（M，依赖 2）
- 目标：新建项目时一键生成标准任务清单；模板可版本化。
- 数据：WorkflowTemplate、TemplateTask；Project 加 template_id / version。
- 后端：模板 CRUD、实例化（复制任务、建依赖、按工期推基线）、冻结规则。
- 前端：向导第三步选模板；简单的模板编辑页（表格即可）。
- 验收：用切片 1 里录好的真实项目反推出第一版模板，再用模板新建一个项目，两者结构一致。
- 不做：模板可视化编辑器。

切片 4：系统会说（S，依赖 2）
- 目标：一键生成日报 / 周报文本，可直接贴到微信。
- 后端：`/projects/{id}/report?range=day|week` 返回结构化 JSON + 文本；内容来自事件表和派生字段，不用 AI。
- 前端：工作流页签“生成更新”按钮 + 复制；助手抽屉复用。
- 验收：文本包含今日完成 / 进行中 / 等待 / 阻塞 / 即将 / 风险 / 落后天数，与页面一致。

切片 5：检查循环、证据、变更记录（M，依赖 3）
- 数据：Task 加 result / round / parent_task_id；TemplateTask 加 requires_evidence；简单 ChangeRecord（或复用 TaskEvent 类型）。
- 后端：检查失败自动建整改 + 下一轮；完成校验证据；变更记录关联预算类别。
- 前端：检查任务的结果按钮；证据上传入口；变更列表。
- 验收：一次失败的检查能形成整改 → 复检 → 通过的链，且下游自动跟到最新一轮。

切片 6：自动化与提醒（S–M，依赖 4、5）
- 完成即解锁下游、前置改期后置平移（必填原因）、逾期自动标风险、每天早上向 Lark 群推日报。
- 验收：不看系统也能在 Lark 里知道今天谁逾期、谁在等。

## 12. 我接下来该做什么

1. 约翻新负责人 30 分钟，带第 10 节的 10 个问题和第 2 节的六阶段图，用最近一套真实房子从头顺一遍，特别是施工内部和三个顺序疑点。
2. 会后把答案回填到本文档第 3 节，把推断改成事实或删除，定下第一版任务清单（预计 30–45 条）。
3. 冻结 MVP 模型：6 态、FS 依赖、关口、等待方、改期必填原因、证据要求。
4. 引入 Alembic，建 Person / Task / TaskEvent 三张表，写状态流转规则（切片 1 后端）。
5. 做工作流页签，把那套真实房子录进去，让负责人试用三天。

9. 只有上面都跑通了，再做检查循环与自动化。
