# VP 进度报告：设计与数据维护说明

更新：2026-09-17。对应 Jira [KAN-40](https://skyvisioninsurance.atlassian.net/browse/KAN-40)。
代码在 [`services/vp_report/`](../services/vp_report/README.md)。

## 这是什么

Jira 的**管理层阅读入口**。开发和 PM 照常在 Jira 维护项目，这个小应用从同一份数据
生成适合手机阅读的进度总览，产出一个可以置顶在微信群里的固定链接。

不懂技术的 VP 打开后应在 30 秒内看懂四件事：
**现在做到哪一步、接下来交付什么、关键日期是什么、哪些事项需要他决定。**

起因：Jira 手机 App 已下线 Timeline 视图（见 `docs/reference/WechatIMG58.jpg`），
手机上看不到甘特图了。网页版 Timeline 仍在，但那是给开发看的，不是给 VP 看的。

**只读。** 报告不提供任何编辑入口，不回写 Jira，不自动替人做验收或上线决定。
所有事实都在 Jira 维护一次，网页自动重绘。

## 一、页面内容 → Jira 来源 → 谁维护 → 什么时候更新

原则：**优先用 Jira 原生字段**；原生字段装不下的业务说明，才写进描述里的固定模板区。
先查重，不新增另一套项目结构。

| 页面内容 | Jira 来源 | 更新负责人 | 更新时机 |
|---|---|---|---|
| 业务主线名称 | 带 `mgmt-lane` 标签的 Epic：管理摘要的「业务名称」，没填则用 Epic 标题 | Ryan | 范围变化时 |
| 主线计划日期 | Epic 的开始日期 / **截止日期（= 承诺日）** | Ryan | 承诺变化时 |
| 主线执行状态 | 该 Epic 下执行单的状态类别汇总 | 开发 / Claude | 每次状态流转 |
| 负责人 | Epic 与执行单的经办人 | 开发 | 分派时 |
| 依赖 | 执行单的原生链接「is blocked by」 | 开发 | 建立依赖时 |
| 会议时间 / 目的 | 带 `mgmt-meeting` 标签的工作项：截止日期 = 会议日期；时刻与目的取自「会议纪要 v1」 | PM | 会前 |
| 会后结论 / 待决问题 | 同一工作项「会议纪要 v1」的决议、待决问题 | PM | 会后 |
| 交付与试用里程碑 | 带 `mgmt-milestone` 标签的工作项：标题、开始日期、截止日期、状态 | Ryan / J | 里程碑确定或改期 |
| 业务摘要 / 影响交付的风险 / 待决策 | Epic 描述「管理摘要 v1」区 | Ryan | 每工作日；会前必核 |
| 验收结果 / 证据 / 确认人 / 确认时间 | 同区：整体验收、验收证据、业务核对人、业务核对时间 | Ryan（业务）/ J（试用） | 验收发生时 |

**缺什么就显示什么。** 页面不会用旧常量顶替，也不会从评论或 AI 推断验收结论。
例如管理摘要没填，那条主线下就会显示「待确认：KAN-36 管理摘要缺：验收证据、需要决定」。

**标签是开关。** 给 Epic 加 `mgmt-lane` 它就上首页，去掉就下来，不用改代码。
里程碑同理——**技术 ticket 默认不是里程碑**，首页只放少量具名的业务节点。

## 二、两个模板

写在工作项**描述**里。**推荐用代码块粘贴**（Jira 编辑器里敲 ```，或粘贴后选「代码块」）：
代码块最不容易被编辑器改格式。手打成普通段落也能解析，但容易漏冒号。
模板区以外的描述内容照常保留，不受影响。

### 管理摘要 v1 —— 放在 Epic 描述里

```text
管理摘要 v1
业务名称：手机操作，电脑同步看到
已经具备：<已核实的业务能力>
还需完成：<剩余的具体交付>
整体验收：待验收 / 已通过 / 未通过 / 待核对
验收证据：<链接；通过时必须填写>
风险判断：按计划 / 有风险 / 待核对
风险或变更说明：<影响、原因及下一步；没有则写"无">
需要决定：<事项与最晚决定时间；没有则写"无">
业务核对人：<姓名>
业务核对时间：<带时区的日期时间>
```

⚠️ **「已验收」的门槛是四样齐全**：整体验收 = 已通过 **且** 验收证据 **且** 业务核对人
**且** 业务核对时间。缺任何一样，页面只显示「待验收」。
执行单全部 Done **不等于**业务已验收——没人签字的「已验收」就是猜的。

### 会议纪要 v1 —— 放在带 `mgmt-meeting` 标签的工作项描述里

```text
会议纪要 v1
开始：14:00
结束：14:45
时区：America/Los_Angeles
参与人：Ryan、J、PM
目的：<会前要决定什么>
待决问题：<还没定的事；没有则写"无">
决议：<会后填；负责人与行动截止日期>
```

⚠️ Jira 的截止日期**只有日期没有时刻**，代替不了 14:00。时刻只从这里读。
结束时间没填就显示「结束时间待确认」，页面**不会**自己补成 45 分钟。
时区没写则按 America/Los_Angeles 解释并标「时区暂定」。

## 三、页面怎么表达状态（避免误读）

这几件事是**分开**的，页面也分开表达：

- **横条长度 = 计划工期**，不是完成百分比。页面不产出总体完成百分比——没有可靠口径。
- **今天线走过 ≠ 完成。** 进展用节点打勾表达。
- **ticket Done ≠ 业务验收。** 全部 Done 最高只到「待验收」。
- **部署成功 ≠ 可内部试用。**
- **承诺日 vs 汇总日**：图上用 Epic 自己的截止日期（承诺）；子项最晚日期另算，
  超出承诺日时在「需要关注」提示，**不会默默把承诺日往后改**。
- **排期冲突是风险事实，不是故障。** 依赖日期矛盾、日期倒置会出现在「需要关注」，
  报告照常可用。

顶部摘要和图中的状态来自同一份计算结果，不会互相打架。
不同主线分别显示「进行中」和「未开始」是正常的。

### 手机排期的阅读方式

排期面板用同一个滚动区域显示主线、执行单和关键节点。横向滑动时，事项名称、
日期和状态固定在左侧；纵向滑动时，日期表头固定在顶部。每一天都有完整列宽，
单日任务也能看见；横条包含开始日与截止日。

- 默认从今天附近开始；可用前后按钮翻日期，或点「今天」返回。
- 点「下一节点」同时定位日期与节点所在行；点主线展开或收起其工作。
- 「放大」让时间表占满当前屏幕，保留同样的固定列与表头；「收起」回到报告。
- 自动刷新保留当前日期位置、表内纵向位置和主线展开状态。仅在本标签页保存阅读位置，
  30 分钟后失效，不保存报告正文。
- 日期缺失时保留已知日期并写明缺什么；日期倒置时提示核对，不画虚假的正常工期。
  会议不会仅因日期已过就被标为完成；交付节点的勾选仍来自 Jira 状态。

新交互的浏览器验证方式与真机边界见[服务说明](../services/vp_report/README.md)。

## 四、多久更新一次

页面自动检查 Jira 更新：打开时、停留期间每分钟、从微信后台切回时，另有手动刷新按钮。
服务端缓存 5 分钟，并发请求会合并成一次查询。

> 对外请这样说：**页面自动检查 Jira 更新，正常情况下最多受 5 分钟缓存和 Jira 索引延迟
> 影响；实际延迟以部署后实测为准。** 不要说"实时同步"。

**怎么识别没更新成功：**

| 页面表现 | 含义 | 怎么办 |
|---|---|---|
| 顶部橙色横幅「更新暂时失败，以下为 HH:MM 的数据」 | 取数失败，显示的是上一次成功的数据 | 通常自行恢复；持续出现找 Ryan |
| 「进度暂不可用」 | 从没成功取到过（常见于服务刚重启 + Jira 配置有问题） | 找 Ryan 查报告服务的 Jira 配置 |
| 「正在同步 Jira 最新进度……」 | 首次打开或服务刚唤醒，正在取数 | 等几秒，页面会自动显示 |
| 页脚「最后成功同步」时间很旧 | 同上，注意这不是页面生成时间 | 点刷新 |

页脚另有「业务核对」时间——那是**人**最后一次确认业务结论的时间，
和「最后成功同步」是两回事：Jira 查询成功，不代表业务结论刚被重新验证。

## 五、访问方式

固定地址 + 首次输一次口令 + 之后本设备保持登录。口令由 Ryan 发给 VP 和 PM。

- 换口令 = 所有旧会话立即失效，**但分享地址不变**，微信群里置顶的链接不用换。
- 这套访问控制**与业务系统完全无关**：不受演示模式影响，也不需要业务账号。
- 报告服务用**专门的只读 Jira 账号**，权限仅够读取所需内容。

页脚会写明本次纳入了多少张执行单。注意：**取完只代表那个只读账号能看到的取完了**，
不等于项目里的全部。当前查询范围（JQL）记录在服务的环境变量里，不显示在页面上。

## 六、日常维护速查

| 谁 | 平时更新什么 | 什么时候 |
|---|---|---|
| 开发 / Claude | 执行单的状态、日期、依赖、经办人 | 开工、提交审阅、出现阻塞、验收结果变化时 |
| Ryan | 三个 Epic 的「管理摘要 v1」：业务摘要、风险、待决策、整体验收 | 每工作日简短核对；关键变化及会前必须核对 |
| PM | 会议工作项的时间与「会议纪要 v1」 | 会前填目的与待决问题，会后填决议 |
| J | 试用里程碑的日期、业务验收标准与反馈 | 范围确认、试用准备、业务验收时 |

只有要**新增展示方式、改字段或接入新项目**时才需要改代码。
日期和工单在 Jira 维护一次，网页自动重绘。
会议上定的事及时回填 Jira——否则聊天记录会变成另一个长期事实来源。
